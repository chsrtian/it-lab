# Phase 15B.4 — End-to-End Troubleshooting Hardening Plan

## Executive Summary

The core architecture is **already decoupled**: the Guide (`GuideOverlay`, `GuideTargetLayer`, `guideProgress`) is an instructor layer that observes completion via `isStepComplete` (actionId/commandId/completeWhen against RunState). Interactive components (`Interactive` 3D wrapper, 2D hotspots, Windows/Linux/Network/Database/Security tabs, terminal) always wire their handlers (`onInspect`, `onCommand`, `onSelect`) regardless of `guideOpen`.

**The failures are content/presentation gaps, not architectural gates:**
1. **TYPE steps show no command text** — GuideOverlay falls back to "run this step's command in the terminal"
2. **Windows Event Viewer target** — guide says CLICK "Event Viewer" but it's a tab button, not a modal
3. **Action Review overlay** — `.sim-feedback` uses `position: absolute` top-right, covers next step
4. **SupportLab conversation** — single scroll container, follow-up chips cover history
5. **No cue↔interaction invariant** — step can advertise CLICK on INSPECT-only target
6. **No cross-domain audit** — 100 scenarios, no machine validation

---

## 1. Single Source of Truth for Commands (TYPE Steps)

### Problem
Terminal commands are hardcoded in `src/engine/terminal.ts` switch statement. TYPE steps have `commandId` but GuideOverlay cannot display the canonical command text + purpose.

### Solution
Create a command registry that both `executeSimulatedCommand` and the Guide consume.

**Files to create/modify:**
- `src/engine/commandRegistry.ts` (new) — canonical array of `{ id, displayText, purpose, shell }`
- `src/engine/terminal.ts` — refactor to use registry; keep allowlist behavior
- `src/features/guide/logic.ts` — add `resolveCommandDisplay(commandId, scenario)` returning `{ text, purpose }`
- `src/features/guide/GuideOverlay.tsx` — for TYPE cue, render:
  ```
  COMMAND
  <code>exact command text</code>
  PURPOSE
  <plain-language explanation>
  ```

### Validation
- Every `commandId` in guided steps must resolve in registry (fail validation test if not)
- `enabledCommands` in scenario still gates availability at runtime

## 2. Cue ↔ Interaction Invariant

### Problem
A guided step can declare `cue: "CLICK"` but its target component only supports INSPECT (no click handler). The ring/card says one thing; the object does another.

### Solution
Add validation in `validateGuidedWalkthrough` (logic.ts) + new audit test:

**For each guided step:**
- `cue: CLICK` → target must have clickable affordance (Windows tab, Linux view button, Network node, Security check, Equipment chain step, Hardware hotspot with `kind: "ui"`)
- `cue: TOGGLE` → target must have toggle control (PSU rocker, service start/stop)
- `cue: CONNECT` → target must be a cable/seatable component
- `cue: INSPECT` → target must open inspector/evidence panel
- `cue: TYPE` → `commandId` must resolve to registry entry
- `cue: OBSERVE`/`VERIFY` → read-only, no fake affordance

**Files:**
- `src/features/guide/logic.ts` — add `validateCueAffordance(step, scenario)` called from `validateGuidedWalkthrough`
- New test: `src/features/guide/cueAffordance.test.ts`

## 3. Action Review Layout Fix

### Problem
`.sim-feedback` (index.css:917) uses `position: absolute; top: calc(...); right: 0.6rem; z-index: 5` — floats over stage, covers next troubleshooting step.

### Solution
Convert to layout region in the stage column (beside/under the environment, not overlay).

**Files:**
- `src/index.css` — remove absolute positioning; make `.sim-feedback` a flex child in `.sim-main` or `.sim-stage` flow
- `src/pages/ScenarioPage.tsx` — move `<div className="sim-feedback">` from inside stage absolute wrapper to a dedicated region in the main grid (e.g., below stage, above rail, or as a collapsible panel)
- Ensure: no overlap, dismissible, internal scroll if needed, small-screen usable

## 4. Conversation Workspace Architecture

### Problem
`SupportLab.tsx` renders conversation log, follow-up chips, ask row, diagnosis row, mentor row all in one `overflow-y-auto` container. Follow-up chips visually cover history; no dedicated regions.

### Solution
Restructure into **three fixed regions** inside the panel (desktop) / bottom sheet (mobile):

```
┌─────────────────────────────────┐
│ Conversation header             │  (fixed)
├─────────────────────────────────┤
│                                 │
│ Scrollable conversation history │  (grows, scrolls internally)
│                                 │
├─────────────────────────────────┤
│ Follow-up question tray         │  (fixed height, horizontal scroll)
│ [suggestion] [suggestion]       │
├─────────────────────────────────┤
│ Ask customer / Diagnosis / Mentor│ (composer area, fixed)
│ [input________________] [Ask]   │
└─────────────────────────────────┘
```

**Reuse for IT Support** — same component, different props.

**Files:**
- `src/features/environments/SupportLab.tsx` — rewrite with CSS Grid/Flex regions
- `src/features/environments/SysadminLab.tsx` (create) — use same conversation workspace
- `src/index.css` — add `.conversation-workspace` layout rules (grid-template-rows: auto 1fr auto auto)

## 5. Hardware Designated-Fix Audit (All Scenarios)

### Scope
100 scenarios across 8 categories. For each Hardware scenario (pc-no-power, pc-on-no-display, printer-*, router-*, switch-*, ap-*, ups-*, patch-*):

1. **Which objects are interactive?** → from `components` + `actions[].component` + `matchHints`
2. **Which action does each invoke?** → `actions[].id` + `kind` + `patch`
3. **Guide OFF interaction?** → click/hotspot/inspect works without guideOpen
4. **Guide ON→OFF preserves interaction?** → no state corruption
5. **2D parity?** → SVG hotspot same actionId as 3D Interactive
6. **3D parity?** → Interactive onClick → onSelect → same actionId
7. **Camera orbit/zoom/preset preserves interaction?** → marker tracks, hotspot clickable
8. **Action produces expected world/evidence?** → patch applied, evidence recorded
9. **Guide detects completion afterward?** → isStepComplete returns true

### Automation
New test: `src/features/guide/hardwareInteractionAudit.test.ts` — loads all hardware scenarios, simulates clicks on each designated fix target with guideOpen=false/true, asserts world patch + evidence + completion.

## 6. Cross-Domain Guide Audit (All 100 Scenarios)

### Machine-Readable Audit Test
New file: `src/features/guide/fullScenarioAudit.test.ts`

Produces rows (conceptually):
```
scenarioId | stepId | cue | targetId | targetResolved | interactionResolved | commandResolved | completionResolved | guideOffInteraction | 2dInteraction | 3dInteraction | status
```

**Validates every guided step:**
- [ ] target resolves to visible component / extraGuideTarget
- [ ] target exists in environment renderer
- [ ] cue is valid enum
- [ ] actionId/commandId/completeWhen present
- [ ] completion trigger resolvable (action exists, command in registry, condition evaluatable)
- [ ] instruction text non-empty (explanation, why, expectedObservation)
- [ ] target label matches canonical target
- [ ] actionable cue has interaction surface (see §2)
- [ ] designated fix available with Guide OFF
- [ ] designated fix still available after Guide ON→OFF
- [ ] actionId resolves to scenario action
- [ ] interaction invokes expected action (patch/evidence)
- [ ] completion can become true (not permanently blocked)
- [ ] TYPE: commandId resolves, command text non-empty, allowlist-compatible

**Single invalid row = test failure.**

## 7. Windows Guided UI Targets Fix

### Problem
Windows tabs (Event Viewer, Task Manager, Services, Device Manager) are **tab buttons** — clicking switches panel content, doesn't "open" a tool. Guide says "Click Event Viewer" (CLICK cue) but the affordance is a tab select.

### Solution
For Windows category:
- Change cues on tab-target steps to **INSPECT** (read panel) or **OBSERVE** (read log)
- If a step must "open" a tool, the target should be the **Checks list button** or **Actions drawer button** that actually triggers the action
- Update all Windows guided walkthroughs (windows-profile-temp, etc.) to match real affordances

**Files:**
- `src/content/scenarios/expansion/windows.ts` — audit & fix cues/targets
- `src/features/environments/WindowsLab.tsx` — ensure Checks/Actions buttons have `data-guide-anchor` for guide targeting
